## 클라이언트 최적화

### 렌더링

- **dpr 상한 1.5** — 고해상도 화면에서 픽셀 수 폭증을 막는다(기본 브라우저 Chrome 기준).
- **가벼운 모드(BUG-12)** — 처음 들어올 때 WebGL 그래픽 장치 이름을 읽어 `Basic Render`·`SwiftShader`·`llvmpipe` 같은 소프트웨어 렌더러(그래픽 가속 없이 CPU 로 그림)면 그림자 끄기, dpr 0.75, 안티앨리어싱 끄기, 풀 무더기 절반. `?quality=low|high` 로 덮어쓸 수 있다(`src/lib/quality.ts`). 같은 헤드리스(SwiftShader)에서 약 2.5배(0.41 → 1.03 fps). 그래픽 가속이 있는 PC 는 그대로.
- **숨겨진 탭 프레임루프 중지** — `visibilitychange` 시 `frameloop='never'` 로 렌더/계산을 멈춘다.
- **원격 플레이어 컬링** — 가까운 12명·반경 72m 만 렌더하고, 25m 밖은 그림자를 끈다.
- **공유 geometry/material** — 같은 색의 원격 캐릭터는 재질을 공유한다.
- **Sky 250ms·Fireflies 20fps 스로틀** — 태양/달/안개/반딧불 위치 계산을 매 프레임 하지 않는다.
- **그림자 맵 1536** — 품질과 비용의 균형. 원거리 그림자는 안개로 가린다.
- **안개(fog)** — 먼 지형/나무를 흐려 컬링 효과와 분위기를 함께 얻는다.
- **인스턴싱** — 나무 360+54그루, 풀 1100, 덤불 260, 돌 90 을 인스턴스 메시로 묶는다.
- **오두막 조명** — 알전구 36개는 InstancedMesh 1개로 묶고, 바닥 스탠드·알전구는 발광 재질만 쓴다. pointLight 는 실내 9개(기본 2 + 2층 펜던트 1 + 벽난로 2 + 달빛 1 + 촛불 2 + 협탁 1)와 바깥 3개(현관 등 1 + 앞마당 외부등 2)다(FEAT-09).
- **절차 텍스처 캐시** — `src/lib/textures.ts` 가 Canvas 로 한 번만 만들고 재사용한다.
- **지오메트리 재사용** — `useMemo` 로 지형/길/울타리 지오메트리를 고정한다.

### 프레임 루프

- 이동/충돌은 `Player.tsx` 의 `useFrame` 한 곳에서만 계산한다.
- 입력은 React 상태가 아니라 `src/lib/input.ts` 의 가변 객체로 읽어 리렌더를 만들지 않는다.
- HUD 갱신은 상태 변경 시에만 발생한다(위치는 소켓 전송용으로만 사용).
- 원격 플레이어는 100ms 배치를 지수 보간으로 부드럽게 잇는다(갱신은 10Hz, 렌더는 60Hz).

### 로딩

- `/forest` 는 클라이언트 캔버스를 `Suspense` 로 감싸 UI 를 먼저 보여 준다.
- 3D 준비 전에도 시작 오버레이/HUD 가 보인다.
- 외부 3D/음원 에셋이 없어 추가 네트워크 요청이 없다.
- Google 프로필 이미지는 `next/image` 대신 일반 `<img>` 를 쓰되 `referrerPolicy` 를 제한한다.

### 사운드

- `AudioContext` 1개, 노드 재사용.
- 사용자 제스처 전에는 노드를 만들지 않는다.
- 음소거는 master gain 만 0 으로 만든다.

## 서버 최적화

- **위치 배치**: 서버는 100ms 마다 모인 이동을 `players:move` 배열 1건으로 보낸다.
  수신자 기준 72m 밖은 보내지 않고 `volatile` 로 밀리면 버린다. 클라이언트는 일괄 `upsertPlayers` 로 1번만 갱신.
- **채팅 fan-out 제한**: 빈터 인원에게만 전송.
- **통계 캐시**: `/api/stats` 60초.
- **불 저장 디바운스**: 4초.
- **DB 풀**: `PG_POOL_MAX=5`, 연결 타임아웃 10초, statement timeout 15초.
- **presence 브로드캐스트**: 5초 주기 + 존 변화 시에만.
- **payload 제한**: `maxHttpBufferSize: 16KB`.
- **레이트리밋**: 토큰 버킷으로 조기 차단.

## DB 최적화

- 인덱스: `visits(user_id)`, `visits(left_at)`, `chat_messages(created_at)`, `audit_events(created_at)`.
- 채팅 조회는 최근 30건만.
- 정리(`db:prune`)로 테이블 크기를 일정하게 유지한다.
- pooled connection string 사용(Neon PgBouncer).

## 다중 접속 비용 모델

40명이 모두 움직이면:

- 전송 패턴: 100ms 배치 1회 → 수신자당 초당 최대 10건만 전송.
- 서버 비교 횟수: 수신자 × dirty(O(N²))지만 값은 좌표 2개만 쓰는 단순 곱셈이라 무겁다 해도 100ms 당 1600번 수준.
- 원격 렌더: 최근접 12명만 그리므로 인원이 늘어도 캐릭터 그리기 비용은 고정.
- 대역폭: 수신자당 최대 ~10 × 평균(사람×구조체 크기). 40명 기준 이동 채널만 약 수십 KB/s 수준.

만약 40명을 넘기거나 지연이 느껴지면 아래 순서로 대응한다.

1. Render 메트릭에서 CPU 사용률 60~70% 시 IP당 연결/정원 재검토.
2. `MOVE_VISIBLE_RANGE` 를 72 → 48 로 줄여 전송량 감소.
3. `MAX_VISIBLE`(12) → 8 로 줄이기, dpr 1.25, 그림자 1024.
4. 그래도 부족하면 v2 Redis adapter + 존 샤딩.

## 병목 진단 순서

1. **fps**: 나무/풀 인스턴스 수, 그림자, dpr, 후처리 유무.
2. **메모리**: 텍스처 캐시가 무한히 늘지 않는지(키 고정), 지오메트리 dispose.
3. **소켓 지연**: 두 탭을 같은 리전에서 열어 비교, 프록시/모바일 네트워크 확인.
4. **서버 CPU**: Render Metrics, `players` 수, 레이트리밋 거부 비율.
5. **DB 지연**: Neon 대시보드의 쿼리 시간, 풀 대기.

## 하지 말 것

- 프레임마다 `setState` 로 HUD 를 갱신하지 않는다.
- 매 프레임 새 `Vector3`/`BufferGeometry` 를 만들지 않는다.
- 그림자 맵을 2048 이상으로 올리지 않는다(모바일).
- 원격 플레이어마다 개별 텍스처를 만들지 않는다(공유).
